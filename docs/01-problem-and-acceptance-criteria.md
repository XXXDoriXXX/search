# 01. Проблема та критерії прийняття

## 1. Постановка

**Вхід:** рядок назви товару. Може бути шумним: `iphone 15 pro 256 чорний`, `Bosch GSR 12V-35 FC`, `Fluke 87V`, `SKF 6205-2RS1`, `Makita DGA504Z`, `Siemens 6ES7214-1AG40-0XB0`, `Смарт-годинник Amazfit GTR 4 Superspeed Black`. Опційно: підказки (категорія, регіон, мова, GTIN, URL).

**Вихід:** один JSON-документ з:

- ідентичністю товару (бренд, виробник, модель, MPN, GTIN[], варіант, категорія, статус життєвого циклу);
- **усіма** атрибутами, які вдалося довести (core + категорійні);
- для кожного поля: значення, одиниця, статус, впевненість, джерела з цитатами, кандидати, метод вирішення конфлікту;
- списком нерозв'язаних полів і причин;
- метаданими прогону (бюджет, раунди, час, вартість).

## 2. Що насправді означає "100% правильно"

Жодна система, що читає відкритий веб, не може гарантувати 100% істинність: виробники публікують помилки, ревізії змінюють спеки, магазини копіюють одна в одної одруківки. Тому вимогу формулюємо так, щоб її можна було **виміряти і виконати**:

1. **Zero fabrication.** Кожне не-null значення має принаймні один evidence span у реально завантаженому контенті, з якого це значення виводиться після нормалізації. Це перевіряється автоматично (grounding check), а не оцінюється LLM.
2. **Verified означає незалежно підтверджено.** Статус `verified` виставляється лише коли значення підтверджують ≥2 незалежні джерела (не копії), або 1 джерело рівня A (виробник, datasheet, регулятор) без жодного суперечливого свідчення.
3. **Abstain замість вгадування.** Якщо докази слабкі або конфліктні, поле повертається як `unknown` / `conflict` з кандидатами. Пусте поле краще за неправильне.
4. **Precision над recall.** На golden dataset точність `verified`-полів ≥ 99.5%. Покриття планується як окрема метрика по тирах.

Це і є практичне "100%": система ніколи не стверджує те, чого не може довести, і кожне твердження можна перевірити за посиланням.

## 3. Тири товарів

| Тир | Опис | Приклади | Очікуване покриття схеми |
|-----|------|----------|--------------------------|
| T1 Mainstream | Масові товари з десятками джерел | iPhone, Samsung TV, Bosch drills | ≥ 95% полів `verified` |
| T2 Long-tail | Є на 3-10 сайтах, часто без структурованих даних | нішеві бренди, регіональні товари, аксесуари | ≥ 80% полів, ≥ 65% `verified` |
| T3 Rare / Discontinued / B2B | 0-2 живі сторінки, PDF, архіви, промислові каталоги | знята з виробництва техніка, промислові компоненти, запчастини | ідентичність + ≥ 50% core-полів; решта з архівів/datasheet |

## 4. Режими роботи

| Режим | Бюджет часу | Раунди | Для чого |
|-------|-------------|--------|----------|
| `fast` | ≤ 8 с p95 | 1 (кеш + anchors + top-структуровані джерела) | UI-автокомпліт, prefill |
| `standard` | ≤ 60 с p95 | до 3 | Основний режим |
| `deep` | ≤ 5 хв | до 8, архіви, PDF, OCR, кроссмовний пошук | Дефіцитні товари, каталогізація |
| `refresh` | фоновий | тільки time-varying поля | Ціни, наявність, статус |

Партиальні результати стрімляться (SSE/WebSocket) з першого раунду, тому клієнт не чекає завершення `deep`.

## 5. Критерії прийняття

Усі критерії вимірюються на golden dataset (див. док 08) у CI. Реліз блокується, якщо будь-який blocking-критерій не виконаний.

### 5.1 Коректність (blocking)

| ID | Критерій | Ціль | Як міряємо |
|----|----------|------|------------|
| AC-C1 | Entity resolution: обрано саме той товар і саме той варіант | ≥ 99.0% (T1/T2), ≥ 95% (T3) | Порівняння anchor identifiers з golden |
| AC-C2 | Precision полів зі статусом `verified` | ≥ 99.5% | Field-level exact/tolerance match |
| AC-C3 | Precision полів зі статусом `single_source` | ≥ 97% | те саме |
| AC-C4 | Zero fabrication: частка не-null значень без grounding span | 0% | Автоматичний grounding check |
| AC-C5 | Конфлікти: для кожного поля з ≥2 різними кандидатами є `resolution` з методом і доказами | 100% | Валідація схеми |
| AC-C6 | Hard-constraints: невалідний GTIN, від'ємна вага, площа ≠ Ш×В тощо | 0 порушень у виході | Constraint engine |
| AC-C7 | Змішування варіантів: значення з іншого варіанта (колір/пам'ять/регіон) потрапило у вихід | ≤ 0.5% полів | Ручна розмітка вибірки + golden |

### 5.2 Повнота

| ID | Критерій | Ціль |
|----|----------|------|
| AC-R1 | Покриття core-схеми T1 | ≥ 95% |
| AC-R2 | Покриття core-схеми T2 | ≥ 80% |
| AC-R3 | Ідентифікація T3 (знайдено MPN або GTIN або сторінку виробника/datasheet) | ≥ 90% |
| AC-R4 | Покриття категорійних атрибутів T1 | ≥ 90% від еталонного набору категорії |
| AC-R5 | Для кожного `unknown` поля вказано, які запити виконані і чому не знайдено | 100% |

### 5.3 Продуктивність та надійність

| ID | Критерій | Ціль |
|----|----------|------|
| AC-P1 | Латентність `standard` | p50 ≤ 20 с, p95 ≤ 60 с |
| AC-P2 | Латентність `fast` | p95 ≤ 8 с |
| AC-P3 | Паралелізм | ≥ 50 одночасних товарів на воркер-пул без деградації p95 більше ніж на 25% |
| AC-P4 | Відмова будь-якого одного конектора | Результат видається, поле `warnings` містить деградацію, AC-C* не порушуються |
| AC-P5 | Ідемпотентність і відтворюваність | Повторний запит з тим самим snapshot-кешем дає ідентичний JSON |
| AC-P6 | Вартість на товар (`standard`) | ≤ узгодженого ліміту (параметр конфігурації, за замовчуванням $0.15) |

### 5.4 Порівняння з бейзлайнами

| ID | Критерій | Ціль |
|----|----------|------|
| AC-B1 | Проти Perplexity (sonar-pro, structured output) на тій самій схемі | Precision `verified` вище ≥ 5 п.п., покриття вище ≥ 15 п.п. |
| AC-B2 | Проти Exa (search + contents + LLM extraction) | те саме |
| AC-B3 | На T3-наборі | Знайдено ≥ 2× більше товарів, ніж бейзлайни |

### 5.5 Пояснюваність та операційка

| ID | Критерій |
|----|----------|
| AC-E1 | Кожне поле має `sources[].url`, `sources[].snippet`, `sources[].fetched_at`, `sources[].authority_tier` |
| AC-E2 | Trace прогону зберігається (запити, відповіді, рішення) і доступний за `run_id` |
| AC-E3 | Source Reliability Ledger оновлюється з кожного прогону та з фідбеку |
| AC-E4 | Time-varying поля (ціна, наявність) мають `as_of` та ніколи не змішуються з immutable-фактами |

## 6. Поза межами (non-goals) першої версії

- Генерація маркетингових описів.
- Порівняння товарів між собою (це окремий сервіс поверх PKG).
- Прогноз цін.
- Гарантований обхід anti-bot захисту сайтів, що явно забороняють автоматичний доступ (політика fetch описана в док 04).
